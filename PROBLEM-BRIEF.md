# Problem Brief — diff2test

## The problem

Large C++ projects often run every test after every change because determining which tests are genuinely affected is difficult. Full suites are safe but slow. Naive selection based on filenames or direct includes is faster but dangerous: a missed dependency can let a regression pass CI unnoticed.

Build systems already produce much of the necessary evidence—target/source relationships, compiler-discovered header dependencies, and registered test commands—but this information is fragmented across formats and usually requires dedicated packages or services to turn into an auditable decision.

## Proposed solution

diff2test analyzes evidence already generated by a CMake-based C++ build:

```text
changed paths
    → affected translation units
    → affected build targets
    → mapped CTest tests
    → selected tests with dependency explanations
```

The program consumes data through files and standard input. It parses the data itself with C++20 standard-library facilities and does not invoke Git, CMake, CTest, a compiler, a shell, or a service at runtime.

## Safety principle

diff2test seeks the smallest test subset justified by available evidence—not the smallest subset it can guess. Any meaningful uncertainty expands selection to the full known suite. If a test catalogue is unavailable, it emits `FULL_SUITE_REQUIRED` so CI can run the complete suite through its normal workflow.

This asymmetry is deliberate:

- **False positive:** an unnecessary test runs; time is lost.
- **False negative:** a necessary test is skipped; confidence is lost.

The product optimizes time only after preserving confidence.

## Target user

The primary user is a C++ developer or CI engineer working on a CMake/CTest project who can generate build metadata during the normal configure/build phase and wants a transparent, local test-selection step.

## Core use case

An external workflow generates CMake File API replies, compiler dependency files, and CTest JSON. It then supplies changed paths to diff2test:

```bash
git diff --name-only origin/main...HEAD |
  ./diff2test analyze \
    --changed-files - \
    --cmake-reply ./build/.cmake/api/v1/reply \
    --dep-root ./build \
    --ctest-info ./build/ctest-info.json \
    --project-root . \
    --explain
```

Git is launched by the user's shell, not by diff2test. The executable only reads stdin and supplied files.

## Product promise

For supported, complete evidence, diff2test will:

- identify affected translation units from changed sources and headers;
- connect translation units to CMake targets;
- propagate impact through relevant target dependencies;
- connect test commands to executable targets when the mapping is provable;
- output selected CTest test names;
- show a human-readable evidence path for each selected test.

When that promise cannot be met safely, it will:

- select all known tests; or
- emit `FULL_SUITE_REQUIRED` when it cannot enumerate the suite;
- explain the missing or ambiguous evidence;
- return a documented status code suitable for CI.

## Why this is a strong zero-dependency project

The project demonstrates substantial first-principles work:

- CLI argument parsing
- JSON parsing with source-position errors
- Make-style `.d` file parsing
- filesystem traversal and path normalization
- graph construction and traversal
- evidence completeness checking
- deterministic human and machine output
- structured error handling

These are capabilities normally assembled from several third-party libraries.

## Differentiators

1. **Conservative by construction:** uncertainty widens the test set.
2. **Explainable:** each selection includes an evidence path.
3. **Local and auditable:** no cloud service, daemon, telemetry, or hidden command execution.
4. **Zero runtime dependencies:** one C++ artifact parses the inputs itself.
5. **Honest boundary:** it does not claim to interpret arbitrary CMake language or infer dependencies absent from metadata.

## Explicit non-goals

- Executing tests
- Generating build metadata
- Launching developer tools
- Parsing arbitrary `CMakeLists.txt` as a programming language
- Supporting every compiler, generator, platform, and CTest wrapper in the MVP
- Predictive or history-based test selection
- Claiming that incomplete evidence is complete
- Replacing a full CI orchestration system

## Judge-facing pitch

> C++ CI wastes time running everything, but unsafe test selection is worse than no selection. diff2test turns metadata your toolchain already produced into an explainable impact graph. When the evidence is complete, it runs less. When the evidence is uncertain, it tells you to run everything. One C++20 source file, zero runtime packages, and no hidden subprocesses.
