# Five-Minute Demo Contract

## Demo objective

In five minutes, prove usefulness, zero-dependency craft, explainability, and safe failure—without making the judge follow a long setup tutorial.

## Narrative

> “Running every C++ test is safe but slow. Guessing which tests to skip is fast but dangerous. TestImpact++ reads evidence the build already produced, selects only what it can justify, and asks for the full suite the moment that evidence breaks.”

## Required environment

- clean public repository checkout;
- supported Linux toolchain;
- demo metadata already generated by documented external commands or generated during the recording before analysis;
- terminal large enough for readable output;
- no hidden aliases/functions that change commands;
- fallback mutation prepared as a reversible copy/move, performed visibly.

## Timeline

### 0:00–0:20 — Hook

Show the problem and safety asymmetry in one sentence. Do not begin with installation.

### 0:20–0:45 — Artifact and rule proof

Show repository tree and point out:

- one implementation source file;
- tests/docs separate;
- no dependency manifest entries or vendored libraries;
- tool never runs Git/CMake/CTest.

### 0:45–1:15 — One-command build

Build from a clean build directory using the documented command. Show the produced artifact.

### 1:15–1:40 — Dependency proof

Show `ldd`/platform inspection and explain that listed libc/libstdc++/loader entries are toolchain/system runtime components permitted by the C/C++ rule, with no third-party application library. Show no dependency downloads in build files/log.

### 1:40–2:40 — Selective success

Supply a changed header and complete metadata. Run `testimpact analyze --explain`. Show:

- one selected test out of several;
- affected translation unit and target;
- evidence path from header to test;
- status `SUBSET_SELECTED`.

### 2:40–3:20 — Broader transitive change

Supply a shared header. Show multiple justified tests and deterministic explanations.

### 3:20–4:10 — Safety fallback

Visibly make one relevant dependency file unavailable or use a prepared incomplete-copy directory. Re-run the same command. Show:

- `FULL_SUITE_SELECTED`;
- every known test emitted;
- precise missing-evidence reason;
- nonzero safety status.

### 4:10–4:35 — Catalogue failure

Use a missing CTest JSON path. Show `FULL_SUITE_REQUIRED` and the instruction to run the normal complete suite. Emphasize that the program invents no test names.

### 4:35–5:00 — Close

Show `STDLIB.md` briefly and close:

> “The optimization is conditional; the safety guarantee is not. Complete evidence gives a smaller suite. Uncertainty gives everything.”

## Commands to freeze after implementation

The final repository README and this contract must contain exact commands for:

1. clean build;
2. metadata generation outside TestImpact++;
3. narrow analysis;
4. shared-header analysis;
5. incomplete-evidence fallback;
6. missing-catalogue behavior;
7. dependency proof;
8. hash/reproducibility proof if attempted.

Do not invent final commands now; fill them after the actual build layout exists.

## Required visible evidence

- public repository identity and commit date inside window;
- single implementation file;
- build succeeds;
- executable runs locally;
- no subprocess behavior;
- smaller correct selection;
- evidence explanation;
- full-suite fallback;
- dependency proof;
- `README.md` and `STDLIB.md`.

## Demo fixture constraints

- at least three tests so one-test selection is meaningful;
- names understandable without domain explanation;
- dependency chain no longer than four displayed edges;
- one shared header for multi-test effect;
- one removable evidence file;
- output fits on screen.

## Recording rules

- target 4:30–4:50, leaving buffer;
- record 1080p if machine permits, terminal font 18+;
- hide notifications and unrelated personal data;
- rehearse twice from a clean checkout;
- keep a backup local recording;
- avoid sped-up sections that obscure verification;
- explain external metadata generation honestly.

## Failure contingencies

| Failure | Demo fallback |
|---|---|
| clean build is slow | begin from clean state, explain wait briefly; never fake it |
| selective fixture fails | do not record; fix before demo |
| metadata generation is verbose | prepare files before recording and show documented commands |
| `ldd` interpretation confusing | use saved text proof plus concise explanation |
| terminal output too long | use controlled fixture and human concise mode |
| recording corruption | keep scripted second take window |

## Demo acceptance checklist

- [ ] Under five minutes
- [ ] Hook within first 20 seconds
- [ ] One-command build visible
- [ ] Single-file implementation visible
- [ ] Zero-dependency evidence visible
- [ ] Selective success shown
- [ ] Explanation shown
- [ ] Full-known fallback shown
- [ ] `FULL_SUITE_REQUIRED` shown or described if time forces one fallback only
- [ ] No claim exceeds documented support
- [ ] Final callout to `STDLIB.md`
